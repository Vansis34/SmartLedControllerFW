## Что это за проект

- Прошивка двухканального LED-контроллера на ESP32 и ESP-IDF.
- Целевая плата из текущего `sdkconfig`: `esp32`, Xtensa, flash 2 MB.
- Артефакты последней обычной ESP-IDF сборки (`build.ninja` и `compile_commands.json`) фиксируют `IDF_VER="v5.1"` и toolchain GCC 12.2.0.
- Проект перенесён на PlatformIO: Espressif32 6.5.0, официальный framework ESP-IDF 5.1.2 (`3.50102.240122`), GCC 12.2.0. Patch-обновление 5.1 → 5.1.2 принято потому, что raw git tag ESP-IDF не является корректно упакованным PlatformIO framework; версии закреплены в `platformio.ini`.
- Контроллер подключается к Wi-Fi через `protocol_examples_common` (`example_connect`) и поднимает HTTP-сервер на стандартном порту.
- Веб-страница встроена в прошивку как `main/www/index.html.gz` через `EMBED_FILES`.
- PWM: LEDC high-speed, таймер 0, 10 бит (0..1023), 3 kHz.
- Каналы: GPIO14 (`LED_1CH_PIN`) и GPIO12 (`LED_2CH_PIN`). GPIO13 объявлен как `RELEY_PIN`, но сейчас не используется.
- MQTT упомянут только в README; реализации MQTT в текущих исходниках нет.

## Карта файлов

- `main/main.c` — запуск NVS/network/event loop, подключение к сети, жизненный цикл HTTP-сервера, глобальное состояние `device`.
- `main/Config.h` — GPIO, времена, enum режимов и общая структура `device_status_t`.
- `main/LEDDriver.c/.h` — LEDC, callback-и завершения fade, очередь команд, FreeRTOS FSM и реализация режимов.
- `main/WEBModule.c/.h` — HTTP endpoints и передача команд LED-драйверу.
- `main/www/index.html` — одностраничный интерфейс управления.
- `main/www/index.html.gz` — реально отдаваемая браузеру копия страницы; после изменения HTML её нужно пересоздать.
- `main/www/zipzip.py` — gzip-упаковка HTML; пути рассчитаны на запуск из корня репозитория.
- `platformio.ini` — закреплённая среда PlatformIO, ESP32 Dev Module, flash 2 MB, monitor 115200, явный путь к исходному `sdkconfig` и объявление встроенного gzip-файла.
- `pytest_http_server_simple.py` — оставшийся тест из примера ESP-IDF; не соответствует текущим endpoint-ам и имени бинарника, поэтому не является рабочим тестом проекта.
- `build/` — существующие артефакты сборки; могут быть устаревшими.

## Модель состояния и режимы

`device_status_t` хранит логическое состояние, режим, проценты и рассчитанные duty:

- `led_state` — включено/выключено.
- `mode` — `MODE_OFF` (0) либо один из пользовательских режимов 1..4.
- `ledBrightness` — общая яркость, UI предполагает 0..100%.
- `halfBrightness` — процент приглушённой яркости; сейчас инициализирован 15, но далее не используется для пересчёта.
- `brightness_1ch/2ch` — верхний duty обоих каналов.
- `halfBrightness_1ch/2ch` — нижний duty режима неполного затухания.
- `timeFade` — длительность fade в миллисекундах; сейчас начальное значение 3000.

Начальное состояние в `main.c`: выключено, `MODE_OFF`, 100%, half 15%, duty 1023/1023, half-duty 153/153, fade 3000 ms.

Реализованные в `LED_StartFade` алгоритмы:

1. `MODE_ALLTIME` — оба канала плавно выходят на заданную яркость и остаются включёнными.
2. `MODE_FADE` — оба канала синхронно идут 0 → максимум → 0.
3. `MODE_FADE_ALTERNATELY` — каналы работают в противофазе: максимум/0 меняются местами.
4. `MODE_HALF_FADE_ALTERNATELY` — противофаза между максимумом и `halfBrightness_*`, без полного выключения.

FSM использует состояния `S_STOP`, `S_IDLE`, `S_FADE_START`, `S_FADE_WAIT`, `S_DELAY`, очередь `CMD_START/CMD_STOP/CMD_SET_MODE`, event group завершения обоих fade и one-shot software timer.

## HTTP API и веб-интерфейс

- `GET /` — gzip HTML.
- `GET /status` — сейчас возвращает `{"lamp":..., "brigh":..., "mode":...}`.
- `PUT /led/ctrl` — UI отправляет `{"state":...,"mode":...,"speed":...}`; обработчик пытается получить только state/mode.
- `PUT /led/settings` — UI отправляет `{"brigh":...,"mode":...,"speed":...}`; обработчик пытается получить только brightness/mode.
- UI предлагает четыре режима, кнопку on/off, яркость 0..100 и скорость 0..100. Скорость скрывается для постоянного режима.

## Подтверждённые недочёты

### Критичные

- **FSM не запускается.** `LED_FSM_Worker` определён, но нигде нет `xTaskCreate...`; `LED_Init()` лишь создаёт очередь/event group/timer. Команды складываются в очередь без потребителя, PWM после инициализации остаётся на duty 0.
- **Небезопасный разбор JSON повреждает стек.** В `/led/settings` переменные `uint8_t brighBuff/modeBuff` передаются в `sscanf("%d", (int *)&...)`; `%d` записывает `int` (обычно 4 байта) в однобайтный объект. Это undefined behavior. Формат также зависит от точного порядка и пробелов JSON.
- **`/led/ctrl` не соответствует фактическому JSON браузера.** Шаблон `sscanf` ожидает закрывающую `}` сразу после `mode`, но UI добавляет `speed`; результат разбора не проверяется. При несовпадении `modeBuff` может остаться неинициализированным.
- **Длина результата `httpd_req_recv` хранится в `int8_t`.** Значения свыше 127 переполняются; нужен `int`/`ssize_t`. Нет цикла для частичного чтения HTTP body.

### Высокий приоритет

- **Скорость не реализована end-to-end.** Поле `speed` игнорируется обоими PUT handler-ами, отсутствует в `device_status_t` как процент, `timeFade` не меняется, `/status` не возвращает speed. После загрузки страницы слайдер остаётся на HTML-default 50.
- **Настройки могут запускать лампу, когда она выключена.** Смена mode всегда вызывает `LED_UpdateMode`, независимо от `led_state`; после запуска FSM это способно начать fade при выключенном устройстве.
- **Ошибки приёма приводят к утечке.** После `malloc` ранний `return ESP_FAIL` не освобождает `buf`; результат `malloc` не проверяется.
- **Нет валидации входа.** state, mode, brightness и speed не проверяются на допустимый диапазон; некорректная яркость способна дать duty выше 1023, неизвестный mode — зависший/пустой алгоритм.
- **Общее состояние читается/пишется из HTTP task и LED task без синхронизации.** Возможны data race и несогласованные поля структуры.
- **Единицы времени software timer неверны/неявны.** `xTimerChangePeriod(delayTimer, device->timeFade * 2, ...)` принимает ticks, а поле описано и передаётся в LEDC как миллисекунды; требуется `pdMS_TO_TICKS`. Итог зависит от `configTICK_RATE_HZ`.
- **При `CMD_SET_MODE` используется `FADE_TIMEOUT` без `pdMS_TO_TICKS`.** Сейчас это ticks, несмотря на имя/значение в миллисекундах.

### Средний приоритет

- `CMD_SET_MODE` содержит недостижимый дублированный блок после `break` (строки около 194–198 в текущем `LEDDriver.c`).
- В ветке `CMD_START` объявляется локальная `bool fade_phase = 1`, которая не используется и затеняет смысл переменной `fadePhase`; фаза при повторном старте/смене режима не сбрасывается детерминированно.
- `MODE_OFF` хранится отдельно от `led_state`, но при выключении `device->mode` сохраняет выбранный режим, а внутренний `current_mode` становится OFF. Контракт стоит явно зафиксировать: выбранный режим и состояние питания — разные сущности.
- Изменение яркости пересчитывает только `brightness_1ch/2ch`; `halfBrightness_1ch/2ch` не пересчитываются. Поэтому нижняя яркость режима 4 остаётся фиксированным duty 153, а не 15% от выбранного максимума.
- В `S_FADE_WAIT` event bits читаются с `clearOnExit=pdFALSE`; очистка происходит лишь при следующем запуске fade. Работает хрупко и требует аккуратной обработки stop/mode-change.
- Stop ожидает окончание предыдущего fade порциями по 200 ms, а затем запускает ещё один fade в ноль; реакция на выключение может быть заметно долгой.
- Возвраты `ledc_*`, `xQueueCreate`, `xTimerCreateStatic`, `xQueueSend`, `httpd_register_uri_handler` не проверяются; при исчерпании ресурсов ошибки скрыты.
- `controller_task_handle`, `last_wake`, `TAG`, `FADE_TIME_OFF`, `RELEY_PIN` сейчас не используются.
- HTTP server запускается после `example_connect()`, а затем ещё может запускаться connect-handler-ом. В текущем порядке handler регистрируется после подключения, однако логика жизненного цикла требует упрощения/проверки на повторный старт и реконнект.
- `nvs_flash_init()` не обрабатывает типичный сценарий `ESP_ERR_NVS_NO_FREE_PAGES` / `ESP_ERR_NVS_NEW_VERSION_FOUND` с erase/retry.
- Нет сохранения настроек в NVS: после перезапуска возвращаются compile-time defaults.
- Нет аутентификации/CSRF-защиты; любой узел в сети может управлять устройством. Допустимость зависит от модели использования.
- Логи печатают полный входной JSON; сейчас секретов там нет, но это стоит учитывать при расширении API.

### Веб и сопровождение

- Исходник HTML содержит следы сохранения из браузера (`saved from`, `operaUserStyle`), лишние комментарии/обёртки и много inline-стилей.
- Интерфейс оптимистично меняет локальный `lampState` до подтверждения ответа; при HTTP 4xx/5xx `.then()` в `/led/ctrl` всё равно считается успехом, поскольку `response.ok` не проверяется.
- Статус загружается только один раз, синхронизации между несколькими клиентами нет.
- Нет ограничения длины body до выделения памяти, корректного JSON parser-а и единообразных JSON error responses.
- `index.html.gz` — отдельный бинарный артефакт и легко рассинхронизируется с `index.html`; сборка не генерирует gzip автоматически.
- В репозитории уже есть незакоммиченные пользовательские изменения и новые файлы. Их нельзя перезаписывать или откатывать без явного запроса.
- В русских комментариях C-файлов при выводе текущей Windows-консолью видна mojibake; сам HTML декодируется как UTF-8. Перед массовой перекодировкой сначала проверить реальные байты/кодировку, чтобы не испортить текст.

## Что уже можно считать существующими фичами

- Два независимых PWM-канала с аппаратным LEDC fade и callback завершения.
- Четыре алгоритма освещения в коде драйвера.
- Асинхронная архитектура команды → очередь → FSM (архитектурно заложена, но из-за незапущенной task пока не работоспособна).
- Плавное включение/выключение и плавное применение яркости для постоянного режима.
- HTTP server с восстановлением после сетевого disconnect/connect.
- Встроенная gzip web page без внешнего хостинга.
- Чтение статуса, включение/выключение, выбор режима и настройка яркости через страницу.
- UI скорости подготовлен визуально, но backend-фичей пока не является.
- Воспроизводимая сборка PlatformIO с закреплёнными Espressif32 6.5.0 / ESP-IDF 5.1.2 / GCC 12.2.0.
- `protocol_examples_common` подключается из поставки framework без локального форка.
- Gzip web page корректно встраивается парой `board_build.embed_files` + `EMBED_FILES`.

## Предпочтительный порядок стабилизации

1. Запустить FSM task и проверить базовый on/off на железе.
2. Заменить `sscanf` на безопасный JSON-разбор (в ESP-IDF обычно cJSON), добавить полный receive-loop, лимиты и валидацию.
3. Определить единый контракт состояния/команд и синхронизацию между HTTP и LED task.
4. Исправить event-bit проверки, единицы ticks/ms, stop/mode transition и сброс фазы.
5. Реализовать speed ↔ `timeFade` и возврат speed в `/status`; определить направление шкалы (100% = быстрее или дольше).
6. Корректно пересчитывать half-duty от текущей яркости либо явно определить его как абсолютный процент полной шкалы.
7. Добавить host/unit-тесты парсинга и переходов FSM, затем hardware smoke-test четырёх режимов.
8. Автоматизировать генерацию `index.html.gz` в сборке и заменить нерелевантный пример pytest.
9. После стабилизации — NVS persistence, кнопка/MQTT, если они действительно входят в roadmap.

## Поток изменения состояния

Эта схема является опорной архитектурой для всех источников команд (WEB, MQTT и
физическая кнопка). Ни один модуль не изменяет состояние LED напрямую: команда
сначала проходит через центральный `AppState`.

```text
WEB task
   │
   ├── получает всё HTTP body
   ├── cJSON разбирает JSON
   ├── формирует patch
   │
   ▼
AppState_Apply()
   ├── захватывает mutex
   ├── s_state → candidate
   ├── patch → candidate
   ├── валидирует candidate
   ├── candidate → s_state
   ├── увеличивает revision
   └── освобождает mutex
            │
            ├── snapshot → overwrite-очередь LED
            ├── dirty mask → notification MQTT
            └── dirty mask → notification persistence
```

Если кандидат не прошёл валидацию, `s_state` и `revision` не изменяются, а LED,
MQTT и persistence не получают уведомлений. В очередь LED передаётся независимая
копия подтверждённого состояния (snapshot), а не указатель на глобальный state.
